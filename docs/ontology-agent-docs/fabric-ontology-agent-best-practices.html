Ontology agent best practices (preview) PREVIEW

The Microsoft Fabric ontology agent builds, improves, and queries ontologies by reading the structure and sample data of your Fabric Lakehouses, Eventhouses, and semantic models. The agent gives better proposals when your workspace is organized. Easy-to-find sources and consistent ontology conventions improve the results.

This article describes practices that help the agent generate accurate, grounded ontology drafts, patches, and queries that are ready to apply.

How to use this guide

This guide is organized into four sequential phases, from organizing your workspace to working effectively with the agent. Each phase builds on the previous one, so apply the practices in order. Skipping prerequisites reduces the quality of the agent's proposals.

Phase 1: Organize your workspace

These practices help the agent find the right sources for your ontology.

Keep the workspace focused

Place the ontology item in the same workspace as the Lakehouses, Eventhouses, and semantic models you want it to model. The agent automatically explores items in the workspace where the ontology lives. If your data is scattered across many workspaces, the agent can only model the slice that lives alongside the ontology.

If you must reuse data from another workspace, copy or shortcut it into the ontology's workspace before you start.

Limit clutter in the workspace

The agent samples Lakehouses and Eventhouses to understand what's available. A workspace with many unrelated items makes the agent's initial discovery slower and noisier. Move experiments, archived items, and unrelated artifacts to a separate workspace so the agent focuses on what matters.

Make sure you have permission to read every relevant source

The agent uses your identity to access workspace data. If you can't read a Lakehouse, Eventhouse, or semantic model, the agent can't read it either. Before you start, check your workspace role. It must grant at least read access to every source you want the agent to consider. Check your role on any shortcut or source workspace too.

Phase 2: Prepare your data sources

These practices make your data discoverable and bindable.

Use clear, descriptive table and column names

The agent reads table and column names as a primary signal when proposing entity types, properties, and bindings. Names that are short, descriptive, and consistent give the agent strong grounding.

Avoid:

  • Cryptic abbreviations that aren't documented anywhere the agent can read.
  • Reusing the same column name for different meanings across tables (it breaks join inference).

Keep identity columns stable and unique

Each entity type in an ontology needs a unique identity. The agent picks identity properties from the columns it sees. Make sure each entity-like table has a stable, unique key column with a clear name.

If your key is composed of multiple columns, add a derived single-column key in your Lakehouse or Kusto Query Language (KQL) table to make binding straightforward.

Add foreign-key columns for relationships

The agent infers relationships by looking for shared keys across tables. Make those keys explicit:

  • In a Lakehouse, add a column on the child table that holds the parent's key.
  • In an Eventhouse, ensure your event tables carry the entity keys they refer to.

When your join keys appear clearly in the data, the agent proposes more accurate relationships and contextualizations.

Use consistent value types

The agent normalizes value types when it drafts entity properties. Inconsistent types across similar columns (sometimes string, sometimes int, sometimes bigint for the same logical column) lead to validation warnings and brittle bindings. Pick a type per logical column and use it everywhere.

For time-series data, include a clear timestamp column

When the agent models telemetry, metrics, or other time-stamped data, it creates a time-series binding that requires a timestamp column. Use a clear, single timestamp column per table (for example, EventTimeUtc) and store values in UTC. Avoid splitting time across multiple columns (Date + Hour + Minute); convert it to a single timestamp first.

Phase 3: Follow ontology design conventions

These practices make ontology drafts ready to apply and easier to evolve.

Use stable, descriptive entity and property names

Entity type names, relationship names, and property names show up everywhere downstream: in queries, in apply results, and in operational dashboards. Choose short, descriptive names that start with a letter and contain only letters, digits, and (for property names) underscores or hyphens. Pick names you'd be comfortable using in a SQL or KQL query a year from now. The agent enforces the exact length and character rules at validation time, and tells you if a name doesn't comply.

Phase 4: Work effectively with the agent

Start in Plan mode

Plan mode is the default for a reason. Use it to:

  • Explore proposals before any changes happen.
  • Compare alternative drafts (ask the agent to redo with different priorities).
  • Double-check validation results.

Switch to Act mode only when you're ready to let the agent apply changes.

Be explicit when you switch to Act mode

When you switch to Act mode, the agent still tells you what it intends to apply before applying. Confirm the scope ("apply just these three changes" vs. "apply everything") and watch for the per-item status the agent streams back as it applies the changes.

Give the agent feedback inside the conversation

If a proposal looks wrong or low quality, say so in the chat, and say why. The agent uses your follow-up to refine its next turn. Specific feedback gets you to a good result faster than vague feedback. For example, tell the agent when it splits one entity type into two that share an ID. That detail helps more than a vague comment such as "this result is bad."

Review the draft preview in the ontology canvas

When the agent finishes a draft in Plan mode, it posts a preview action in its chat message. Open it: the Fabric ontology canvas renders a read-only preview of the proposed ontology, and it's the best surface for reviewing what the agent is about to do.

  • For a new ontology, walk the proposed entity types, properties, data bindings, and relationship graph in the canvas before you switch to Act mode. The canvas shows the structure exactly as the agent creates it.
  • For an improvement, look at the change indicators and the per-item explanations to confirm that the agent is changing what you wanted, and only what you wanted. Pay extra attention to items flagged as removed; they appear in the preview so you can confirm the deletions on purpose.

The preview is read-only: to adjust the draft, ask the agent in the chat and open the next preview action it posts. Switch to Act mode only when the canvas matches what you want.
